研究四 V13 编码提示词（整合版）

任务：阅读输入对话，按目标连续性划分任务；对任务起手、逐动作功能及目标成果分别编码。动作只使用截至当前用户请求的前缀；成果使用对应目标的完整证据。保持源ID、消息ID和输入hash，按附带结构输出JSON。

成果规则：对每个局部目标、目标版本与整体任务分别判断。先核对实际要求及验收条件，再检查回复和后续有效证据。A为有依据的达成，B为有依据的未满足，C为完成核查后仍缺决定性证据，D为不具有可评价目标。未完成判读用review_pending，不能改成C或no。无回复的新目标记录右删失；此前独立达成的目标仍保留。用户自行修复另记贡献来源。明确数量、格式和技术条件须逐项核对；需要外部事实时记录核查来源及时间。

同一位置可以含多个功能。逐类作yes/no/uncertain判断；尚未判读用not_reviewed。对阳性、任务边界和成果记录消息ID、原文引文及判断依据。

## 二、分析对象、数据单位和观察窗口

### 2.1 数据层次

| 层次 | 字段示意 | 定义 | 主要用途 |
|---|---|---|---|
| 源会话 source_case | `case_id`, `source_key` | 一条完整原始人机交互记录 | 原文、抽样及右删失情况 |
| 工作流/任务 workflow_task | `workflow_id`, `task_id` | 用户持续追求的可识别目标；可含子目标 | 21类起手、整体成果Q1–Q9 |
| 用户局部请求 local_request | `message_id` | 当前一条用户消息提出的内容或变更 | 局部成果、修订及右删失 |
| 相邻用户动作 adjacent_action | `prev_user_message_id`, `current_user_message_id` | 当前用户消息相对紧邻前一条用户消息的语义功能 | C01–C15、任务关系、方面切换 |
| 目标版本 goal_version | `goal_version_id` | 同一任务内要求、交付范围或硬约束发生有效修改后的阶段目标 | 首次达成、失效、替换、完整过程结果 |

一个源会话可含多个任务，一个任务可含多个用户请求和目标版本；一套练习可由一个工作流与多个可检验的单题子目标构成。

### 2.2 源信息不可变

保留 `case_id`、`source_key`、`unit_id`、`input_hash`、原文件路径、消息顺序、speaker、`message_id`、原文和需要的时间戳。引用证据用**原始消息ID＋逐字引文**，不能虚构、截改成另一个意思或只引用无法定位的摘要。若重建 task_id，必须记录新旧映射与原因，不能修改原文hash。

### 2.3 观察窗口

- **资格、任务起手、动作、task_relation、ASPECT_SWITCH**：只读取**当前用户消息及在它之前实际存在的对话前缀**。判定后应锁定；后续纠错不能倒改历史意图。
- **局部/目标版本/整体成果**：必须读取该目标的**实际助手答复、随后的用户反馈、交付物、修复记录和必要外部资料**，可使用目标之后的有效证据。
- 能够在同一完整文件内看到未来原文，不等于允许使用它判断过去动作；记录实际观察窗口。

### 2.4 计数关系

在没有空消息/系统特殊记录干扰时，一个有 n 条有效用户消息的源会话，通常有 n−1 条相邻动作；跨源不拼接。首条用户消息需要起手，但不作为该源内部的相邻动作。**每条非空用户消息原则上且仅归属一个直接任务**；涉及多个明确目标时，用同条消息的 `subgoals` 表示，必要时按可独立交付的目标拆任务并标注同源消息关联，避免重复计算消息数。

## 三、资格、语言与任务起手前置判断

### 3.1 当前统一资格层

资格仅用于分层统计，**不作为C01–C15是否允许编码的硬过滤器**。同一研究可分析信息请求与非信息请求，但必须分别报告。

- `explicit_information`：明确索取事实、解释、证据、核验、比较、方案、可知知识或判断信息。
- `not_information`：纯寒暄、致谢、停止、单纯抒情、仅创作/润色/翻译/格式操作且无实质信息索取；这些仍可能有有效C09/C10动作和可评价成果。
- `mixed_or_unclear`：信息目的与其他目的不可分、只有关键词/材料无法识别具体目标，或需要前文才能确定但前文缺失。

不得仅因包含英文单词、数字、代码或附件就视为信息查询；不得因为资格外就删除该段的动作和交付记录。比较“原资格口径”时，另存 `legacy_eligibility`，不覆盖本版判断。

### 3.2 语言判断

从**用户实际自然语言文本**判断语言，可用 `zh`、`en`、其他语言码、`mixed`、`undetermined`。多个语言均有独立自然语言片段才记mixed；单纯专有名词、代码变量、英文产品名不一定构成混合语言。语言标签与可否理解或成果正确性分别记录。翻译任务的**源语与目标语**另行记录。

### 3.3 裸关键词、纯材料及无目标输入

只给术语/人名/文章/代码片段不自动表示“解释”“翻译”或“修复”。保留 `opening_form=keyword_seed/material_provided`，必要时 `primary_subtype=UNCLEAR`、`missing_information=goal`。**可识别有目标但条件不足：通常成果C；完全不能识别可评价目标：D。** 不能因为助手后来猜测并回答，就回填先前用户起手为明确任务。

## 四、任务划分、任务关系与目标版本

### 4.1 基本裁决顺序

逐条确定：①此时具体目标是什么；②它是否延续紧邻目标；③是否属于先前存在任务的返回；④有没有新硬条件或独立交付；⑤应建立新任务、子目标还是goal_version。先划边界，再统计成果。

### 4.2 判为 `same_task` 的常见情形

原目标下补充条件、扩大/收窄范围、要求继续、换表达、纠错、补材料、要求再给几例、改写同一产物、同一清单采集流程依次更换查询对象。此时通常复用 task_id，可新建 goal_version 或局部子目标。**只换查询对象不自动新建任务**。

### 4.3 判为 `new_task` 的情形

核心目的或可独立交付物与紧邻任务无持续依赖，例如前面问代码插件配置，后来独立问另一个框架原理；先写商业邮件，再要求翻译游戏公告。**同主题≠同任务**；相反，不同对象也不必然是不同任务。

### 4.4 返回旧任务

若 A任务→B任务→返回A：相对紧邻B的 `task_relation=new_task`，但 `task_id` 应复用A，另填 `return_to_task_id=A`。禁止为返回而人为增加一个全新任务分母。

### 4.5 连续练习与重复追问

一个“做完这一套题”的上位目标可以是一个工作流；每道题记一个独立子目标和 `local_result`。同一道题原样重发，通常判重复/重新索取而非全新任务。多道题跨入明显不同的独立学习目标时，分为多个任务并保留工作流关联。

### 4.6 目标修改与有效范围

- `goal_extension`：新增必需部分，保留旧条件；仅新部分未答，不抹掉旧局部A。
- `goal_replacement`：用新条件替换旧条件；新版本按**新条件**验收，旧版错误/成功留历史。
- `goal_withdrawal`：撤回不再要求的条件；撤回后的总体验收不应继续把该旧条件当作硬门槛。
- `optional_addition`：如果“再给一些”只是可分离的额外请求，原先完成的主任务可以保持A，新请求单独记录右删失或C；如果用户明确将追加部分设为整体必需交付，整体状态按最新有效完整目标评估。

### 4.7 关系证据与不确定性

`task_relation` 取 `same_task`、`new_task`、`uncertain`，不能只依话题相似度、关键词或数值变化。边界不清标 `boundary_uncertain=true`，写明 competing interpretations；不以新类别掩盖边界不明。每个任务保存 `task_start_message_id`, `task_end_message_id`, `user_message_ids`, `goal_versions`, `subgoals`, `return_to_task_id`。

## 五、任务起手：21个细类与全部辅助字段

**起手每个任务判一次；目的标签与动作标签分开。** `primary_subtype` 主类单选，确实有两个同等目标可用 `MIXED` 并记录 `secondary_subtypes`；无法判断用 `UNCLEAR`，不能为了占满类别而猜测。以下是当前21细类的基本含义和边界。

| 编码 | 细类 | 判定要点 |
|---|---|---|
| F01 | 实体、名单、事实定位 | 找已存在的实体身份、名单或具体事实；非偏好推荐 |
| F02 | 已有数值、时间、地点 | 查已公布的数量、日期、地点、安排；不含自己求算 |
| F03 | 来源定位与真伪核实 | 起手就是找证据、验证说法、查出处 |
| E01 | 概念、术语、定义 | 问某个概念是什么意思 |
| E02 | 原因、机制、原理 | 问为什么、如何发生、底层作用机理 |
| E03 | 材料或现象解读 | 问一段原文、图表、情境具体表达何意 |
| P01 | 操作方法与步骤 | 要实际步骤、实施路径或操作办法 |
| P02 | 故障排查 | 已出现错误、故障、异常，要求诊断修复 |
| P03 | 计算、证明与练习 | 要具体解题/证明/考试练习结果 |
| D01 | 比较异同 | 比两个或多个对象差别 |
| D02 | 价值、适用性评价 | 问是否合适、值得、利弊与风险 |
| D03 | 筛选与推荐 | 按用户偏好或约束推荐选择 |
| X01 | 主题总体概览 | 对领域或话题开放了解 |
| X02 | 学习、研究或探索路线 | 请求可行方向、路线、进阶安排 |
| X03 | 需求、偏好澄清 | 要帮助明确需求或选择标准 |
| A01 | 新内容/新产物生成 | 从无到有写文章、邮件、代码、方案等 |
| A02 | 已有产物修改 | 修订、改写、删补、纠正已有内容或代码 |
| A03 | 翻译、改写、格式转换 | 核心目标是跨语言、表达形式或结构转换 |
| M01 | 助手/AI元信息 | 问AI身份、能力、访问权限、模型或可完成事项 |
| Y01 | 未来预测与假设推演 | 未确定的趋势、预测、条件假设后果 |
| S01 | 经验与社交回应 | 征询经验、感受、对话回应；不可推定AI真实个人经历 |

**重点区分**：已有数字F02，求解数字P03；比较差别D01，适不适合D02，具体推荐D03；问如何做P01，已报错要排错P02；要求写新内容A01，修改旧内容A02，仅翻译/格式转换A03。起手目的不因助手之后交付了什么而改变。

### 5.1 必须完整填写的起手辅助字段

| 字段 | 取值/说明 |
|---|---|
| `primary_subtype` | 21细类之一 / `MIXED` / `UNCLEAR` |
| `secondary_subtypes` | 其他确实并列的细类，多选；无则空 |
| `output_forms` | `entity_list`, `number_judgment`, `explanation`, `steps`, `code_config`, `text_plan`, `translation_format`, `other_unclear`；至少一个 |
| `goal_clarity` | `clear`, `partial`, `unclear`；仅看用户目标是否可识别，不是答案能否查到 |
| `background_present` | `yes`, `no`, `uncertain`；当前起手是否给背景/现状/尝试 |
| `constraints_present` | `yes`, `no`, `uncertain`；是否有明确必须、禁止、时间、预算等 |
| `constraint_types` | `format`, `length`, `budget`, `time`, `scope`, `audience`, `technical`, `must_or_avoid`, `interaction`, `other` 多选 |
| `checkable_deliverable` | `yes`, `partial`, `no`, `uncertain`；起手是否可观察何为交付，与实际成败无关 |
| `context_dependence` | `yes`, `no`, `uncertain`；理解这句话是否需要之前上下文 |
| `opening_forms` | `direct_request`, `keyword_seed`, `material_provided`, `symptom_report`, `context_reference`, `capability_probe`, `compound_request`, `statement_or_opinion` 多选 |
| `missing_information` | `object`, `goal`, `referent`, `material`, `none` 多选；`none` 不与其他并用 |

每个确定的主/次需求、存在的背景与约束、明确起手形式应有 `message_id + 逐字quote + 简短reason`。对不存在的内容不能编出证据。起手只看本任务首次可识别需求及必要先前前缀，不用未来回复回填。

## 六、15类动作语义编码：全部62个细类

每条相邻动作依功能逐类独立判定。**15类均可用于新任务起点的当前功能**，但C01、C05、C06等需要真实先前依存关系的标签，不能凭空把新任务首问判成“修改了上一任务”。一条动作可同时命中多类；同一大类也可命中多个细类。

### C01 延伸信息请求（5细类）

| 细类 | 何时判yes | 不能机械判yes的情形 |
|---|---|---|
| C01.01 属性补问 | 沿用同一对象补问另一个属性/信息 | 独立新对象的新事实首问 |
| C01.02 增加对象 | 原查询/比较集合新增一个对象 | 改成无关独立任务 |
| C01.03 换对象沿用问法 | 在稳定工作流中换人、词、产品继续同类问题 | 每次换对象都认为主题/方面切换 |
| C01.04 补查条件 | 在同一目标下查更多情形或适用条件 | 用户直接纠正旧答案，应另看C03 |
| C01.05 继续比较 | 原比较目标下继续补比较维度或对象 | 全新独立比较首问只需C12 |

边界：C01描述**原信息目标的延伸**；必须保存可识别的前一目标证据。可同时C11（当前具体事实查找）或C12（继续比较）。

### C02 解释、举例与推导（5细类）

| 细类 | 何时判yes |
|---|---|
| C02.01 概念解释 | 明确要求解释术语/定义 |
| C02.02 原因机制 | 要求说明为什么、机制或原理 |
| C02.03 举例 | 要求给实例、反例或示范 |
| C02.04 推导 | 要求展开计算、证明、论证、推导过程 |
| C02.05 步骤说明 | 要求解释怎么做的步骤 |

只要求“算出数值/选出选项”优先C14；明确“写出过程”可同时C14与C02.04。仅一句“继续”不能自动赋C02。

### C03 核验、质疑与纠错（4细类）

| 细类 | 何时判yes |
|---|---|
| C03.01 确认旧答 | 对助手此前答案问“确定吗”或验证其成立 |
| C03.02 指出矛盾 | 明确指出前后论断、条件或结果不一致 |
| C03.03 要求复核 | 要求重新检查计算、资料、推理、引用 |
| C03.04 要求更正 | 要求修改已确认或用户指出的错误 |

仅新增事实问题不是纠错。一次“你答错了，请给出处并重写”可同时C03、C04、C09。用户给出低分不自动等于每道题均被用户否定。

### C04 资料、来源与证据索取（4细类）

| 细类 | 何时判yes |
|---|---|
| C04.01 论据来源 | 索取支持当前说法的证据或出处 |
| C04.02 原文 | 要原文、原始记录或原始文件 |
| C04.03 参考资料 | 要书目、研究论文、资源材料 |
| C04.04 资源链接 | 要网址、下载入口、DOI链接或其他访问入口 |

一个请求可同时C04.03和C04.04（例如“列出论文并给DOI”）。不能仅凭出现“论文”就把普通综述写作任务判C04。

### C05 调整需求范围与条件（5细类）

| 细类 | 何时判yes |
|---|---|
| C05.01 收窄 | 对象范围、数据范围或允许集合收窄 |
| C05.02 放宽 | 撤销限制、扩大允许集合 |
| C05.03 替换范围 | 将旧范围/对象集合替换成新范围 |
| C05.04 技术条件 | 新增/替换工具、环境、版本、语言或技术限制 |
| C05.05 接受标准 | 改动预算、时限、质量门槛、字数等验收标准 |

要能指出**旧条件与新条件**。单纯交新材料属于C07；仅排版成表格通常C09.03；指定新的独立任务不是凭空修改上一任务条件。改预算也可能是C05.05，视要求实质而定。

### C06 修复或重新表达问题（4细类）

| 细类 | 何时判yes |
|---|---|
| C06.01 明确重述 | 用户明确纠正自己的表达或重新定义问题 |
| C06.02 逐字重问 | 在未得到满足时再发同一问题 |
| C06.03 隐式重问 | 换句话重新索取原本想要的同一信息 |
| C06.04 指代澄清 | 说明此前“它/这个/那段”的指代 |

与C03区分：C03针对**助手答复**，C06主要针对**用户问题表达**。仅换一个同类对象不是重问；继续流程通常C08。

### C07 补充输入与回应澄清（5细类）

| 细类 | 何时判yes |
|---|---|
| C07.01 背景 | 提供当前处境、已有尝试或背景信息 |
| C07.02 材料 | 上传文章、代码、文件、截图等供处理材料 |
| C07.03 数据 | 提供数值、参数、观测值、报错日志中的数据 |
| C07.04 回应提问 | 回答助手要求的澄清、练习或确认问题 |
| C07.05 选择 | 明确从助手所给方案中选择一个 |

材料/数据可以同一消息出现多个细类。纯提供材料不自动表示已提出翻译或修改目标；还须审读有没有明确指令。

### C08 推进、继续与追加产出（4细类）

| 细类 | 何时判yes |
|---|---|
| C08.01 继续 | 要继续尚未完成的工作 |
| C08.02 追加更多 | 再给几个同类型例子/产出 |
| C08.03 下一部分 | 按计划进入下一章/下一包/下一题 |
| C08.04 恢复流程 | 恢复之前中断的工作 |

“继续”不等于满意或此前已完成。与C14（下一道题）、C09（下一篇产物）、C02（继续展开解释）可并列，但是否为新任务仍要单独判断。

### C09 生成、加工或应用产物（6细类）

| 细类 | 何时判yes |
|---|---|
| C09.01 新产物 | 新写文章、报告、代码、表格、计划、邮件等 |
| C09.02 编辑修改 | 修改、补写、删改既有产物 |
| C09.03 格式转换 | 转成表格、列表、指定版式或结构 |

## 七、动作编码的值、并列标签、证据与覆盖

### 7.1 逐类别值

- `yes`：当前动作确实实现该类功能；必须填写一个或多个合法 `subtypes`，给出当前用户原文精确证据。
- `no`：已经逐字审读该类定义与当前前缀，能够排除；细类和正向引文留空。
- `uncertain`：已经审读但存在真实语义歧义、上下文缺失或类别边界冲突；填 `uncertain_reason`，不可伪装成no。
- `not_applicable`：只有字段确实结构不适用时采用，并说明为什么；不能泛用来隐藏未审读。
- `not_reviewed`：**审计/工作进度状态**，不是正式语义判断；该类别根本尚未独立复核时必须如实保留，正式统计不当阴性。

一个动作可 `C03.03 + C04.01 + C09.02`；不能强制单主标签。已审读的15类全面确定且至少有一个yes，`coverage_status=classified`；全no、有uncertain或真正无法归类时记 `unresolved` 并写缺口；没有可分类的有效行为才记 `not_applicable`。若仍有`not_reviewed`，计入 `review_incomplete`，不得声称整个动作已正式分类完成。

### 7.2 证据要求

每条yes至少一条 `evidence={message_id,quote,reason}`；quote逐字匹配当前用户消息，解释关系时另引先前前缀。`task_relation`及`ASPECT_SWITCH`各有独立关系证据。不能只凭关键词；不因缺某个关键词否定真实语义。`uncertain`应写清待证问题。

### 7.3 真正的分类缺口

若15类确实不能表达当前行为，记录 `taxonomy_gap`、`gap_description` 和建议细类；不立即把它合并进入原C01–C15。**类别修改要提出新版本，并在历史数据上做影响评估**。全15类候选命中率、完全审读率、细类间一致性与真实正确率必须分开汇报；覆盖率不是准确率。

## 八、ASPECT_SWITCH 方面切换

这是独立指标，**不是第16类，也不直接提高C01–C15的覆盖率**。

仅 `task_relation=same_task` 时取 `yes/no/uncertain`；`new_task`或`uncertain`关系时通常 `not_applicable`。

- `yes`：整体目标不变，但关注的**实质信息维度/子问题/对象属性**转向另一方面。例如同一电脑选择目标先比较价格，后比较续航。
- `no`：重复同一个维度、同一问法换实体但关注属性不变、要求更详细解释同方面、仅改排版或数值条件。比如先问A的安全性后问B的安全性，不应仅因为对象换了就自动标yes。
- `uncertain`：整体目标同一，但无法确定是否有实质焦点改变；写前一焦点、当前焦点和缺失的信息。

每条记录写 `previous_focus`、`current_focus`、`overall_goal`、`evidence`。方面切换与成果成功/失败无直接推论关系。

## 九、成果判定：局部、版本与整体全部完成判断

## 十一、成果九题Q1–Q9：字段、代码与证据

本手册保留既有九题的**字段与代码兼容性**，但统一改用本版的“直接验收＋合理外部核验”证据标准；旧“不能联网查证”条款**失效**。Q2完成**不等于**九题全部完成。

| 字段 | 内容 | 取值及要求 |
|---|---|---|
| `q1a_msg` | 任务目标首次出现位置 | 原始用户消息ID，不得编造 |
| `q1a2` | 目标是否可识别 | `1`能；`2`不能；`3`无法判断 |
| `q1b` | 任务边界 | `1`清楚；`2`起终边界不清；`3`是否独立任务无法判断 |
| `q1c` | 目标/条件如何变化 | `1`无明显变化；`2`扩展新增；`3`替换/撤回；`4`无法判断 |
| `q2` | 整体成果 | `A`已达成；`B`明确未满足；`C`未知；`D`不适用 |
| `q3` | A的达成证据类型（单选） | `1`可核实助手成果；`2`用户明确确认；`3`两者都有；非A留空 |
| `q3_msg`, `q3_speaker` | 首次有依据达成位置、说话者 | 原始消息ID；`U`用户、`S`助手、`X`不能确认；非A留空 |
| `q4` | B的证据类型（多选） | `1`有可确认实质错误；`2`用户明确未解决/不符合；`3`明确失败后放弃；`4`其他（写明）；非B留空 |
| `q4_msg` | B最关键证据 | 原始消息ID；非B留空 |
| `q5` | C的未知原因（多选） | `1`对话结束且尚缺必要确认；`2`关键真值核验后仍无法确认；`3`真正依赖主观验收；`4`缺原文、执行、结果或后续答复；`5`目标条件/边界不清；`6`证据冲突；`7`其他；非C留空 |
| `q6` | 子目标达成 | `1`至少一个可确认子目标达成；`2`有子目标但未确认达成；`3`无独立子目标；`4`无法判断 |
| `q6_msg`, `q6_speaker` | 首个已达成子目标位置 | q6=1时填原始ID及U/S；否则留空 |
| `q7` | 首次回答之后的反证/目标变化 | `1`无；`2`有反证；`3`目标扩展/变更；`4`不确定；反证与变更都有时优先2 |
| `q7_msg` | 反证/目标变化位置 | q7=2或3时填对应消息ID，否则留空 |
| `q8` | 此任务最后消息之后的用户行为 | `1`转独立新任务；`2`说未解决/放弃后换题；`3`继续同任务；`4`对话结束；`5`其他 |
| `q9` | 成果判断把握程度 | `H`高；`M`中；`L`低；不直接等于核验等级 |

多选使用英文分号 `;` 分隔，不能混用分隔符。`q3`仅A填，`q4`仅B填，`q5`仅C填；缺终审应使用**另外的**`review_status=review_pending`，不能把`review_pending`塞入正式数值代码。

### 11.1 Q1精细边界

- Q1a2：部分明确的目标不应直接判“不能识别”；例如对象未指明但知道用户要解释它，可视为“可识别但部分信息缺失”，具体说明。
- Q1b：看**指定任务**的边界，而不是整份源会话是否还有其他任务。
- Q1c：一般“再解释详细些”不构成独立目标改变；新增硬条件或目标确实扩大记2，替换/撤销旧条件记3，两者同在优先3。

### 11.2 Q2裁决顺序

先排除无目标D；再看最终**未修复的实质失败**B；再看可核实的全部必要交付/明确用户确认A；剩余经充分审查仍未知C。此顺序是审计工具，不代表可以只挑一个孤立早期错误覆盖后来的修复。

### 11.3 Q3与Q4

Q3位置应是目标**第一次达到完整A标准**的位置，不是随便一个助手回答。若后来有效反证使A失效，应记录失效而重新判最终状态。Q4记录当前未修复的主要失败及可选并列原因；“要求更详细”不自动等于用户不满意。

### 11.4 Q5额外明细要求

**旧q5编号只是粗分类**。新版每个C还必须有 `c_reason_codes`、`missing_evidence`、`verification_attempts`、`verification_status`、`censor_scope`，用来证明已合理核实仍未知。`q5=1`不能独立因用户没说谢谢而成立；只有某必要的可观察完成确实依赖缺失反馈时才可使用。

### 11.5 Q6与Q7

Q6对**可独立核查的子目标**另行计数，整体C也可能q6=1。Q7针对首次答复之后的实际反证/目标变化，正常继续追问不自动等于反证。既有反证又有变化时优先2，另在审计日志保存两个事实。

### 11.6 Q8和Q9

Q8记录的只是结束现象，**不是成功率指标**。任务最终结束后再无用户消息用4；有后续独立目标用1；若明确未解决放弃后换题用2。Q9应根据任务定义、证据完整度和结论把握综合给H/M/L，不能把C一律L或A一律H。

## 十二、过程成果：目标版本的状态

为兼容早期目标过程研究，仍单独保留过程状态，但**不与Q2的A/B/C/D直接互换**：

| 状态 | 精确定义 | 与Q2关系 |
|---|---|---|
| `C_EVIDENCE` | 某目标版本有可核实助手成果 | 可能支持局部/版本A，不自动支持全任务A |
| `C_USER` | 用户明确确认具体目标解决或理解 | 可能支持A，但要看是否有后续核心反证 |
| `C_SWITCH` | 用户换到独立新任务，仅表示行为推定 | **绝不直接证明A或B，也不可机械映射C** |
| `M` | 某目标版本存在实质未满足、明确失败或拒绝 | 可支持局部/版本B，是否最终B看后续修复 |
| `U` | 某版本仍缺材料、真值、执行或目标证据 | 需按新版必要外部核验纪律复查 |
| `X` | 没有可评价任务 | 与D接近，但必须按对应层级判断 |

每个目标版本保存：`goal_version_id`, `goal_scope=task_goal/subgoal`, `goal_quote`, `goal_message_id`, `status`, `first_attained_at`, `evidence[]`, `goal_adjusted`, `invalidated_at`, `reason`, `verification_method`。EVIDENCE/USER的达成位置必须可定位；M需要具体失败依据；U必须说明查过什么还缺什么。
